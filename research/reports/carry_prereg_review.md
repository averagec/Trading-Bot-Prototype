## Verdict: FIX FIRST (not BLOCK)

The economics and the code are sound: accrual, orientation, alignment, look-ahead and the late-NOK handling all check out under independent probes, and the design is honest about power. Three things must be fixed before the DEV run is authorised, all cheap: the "freeze" is not an external freeze; the FINAL outcome taxonomy has a hole; and the primary null is anti-conservative in plausible worlds the calibration never tried, so two sentences in section 8 ("false positives are controlled") are not supported. Category E stays well protected (false-E rate at most 4 % in the worst world I built); the exposure is to category P and to the G1a/G1b claims.

## Must-fix items

**M1. The pre-registration is not actually frozen, and a re-run can overwrite the first result.**
- Where: `git status` shows `?? research/reports/carry_prereg.md`, `?? research/fx_carry.py`, `?? research/tests/test_fx_carry.py`, `?? research/reports/carry_prereg.sha256`, `?? research/data_multi/` (nothing in git). `fx_carry.py` `freeze()` / `check_prereg_frozen()` (lines 108-123) only compare the prereg to a hash file that the same CLI writes; code and data are not hashed into the freeze; `run_dev()` (line 673) writes into `OUT_DEV` without checking that `summary.json` already exists. R3-1 was committed (fc8c4cf) before its run and `progress.md` (2026-10-31) says "commit preregs before runs next time".
- Why it matters: anyone (including a motivated later session) can edit the code, re-run `freeze`, re-run `dev`, and overwrite the first result; section 10 allows "bug fixes with the first result kept on record" but nothing keeps it. The header claim "FROZEN BEFORE ANY RUN" has no external timestamp.
- Minimal fix: commit prereg + sha256 + `fx_carry.py` + `carry_screens.py` + tests (not the data) before the run; store the code sha256 and sha256 of the ten rate CSVs and nine parquet files in the freeze file and have `dev` refuse on any mismatch; make `run_dev` refuse (or write to a new timestamped folder and keep the old) if `summary.json` exists; add one sentence to section 10: a post-result bug fix needs a test that fails before the fix, and both results are reported.

**M2. FINAL taxonomy (section 9) is not exhaustive.**
- Where: section 9. CONFIRMED = all of (i) to (v). CONSISTENT BUT NOT CONFIRMED = "S1 point Sharpe > 0 and (i) fails". NOT REPLICATED = "S1 point Sharpe <= 0". A result with S1 Sharpe > 0, (i) true, and any of (ii) to (v) false belongs to no category (for example the lower bound is above 0 but dropping JPY flips the sign, which is exactly the case section 9 is built to catch).
- Why: an undefined outcome on the one unburnt window is where a post-hoc label gets chosen.
- Minimal fix: define CONSISTENT BUT NOT CONFIRMED as "S1 point Sharpe > 0 and not all of (i) to (v)"; state that the report lists which of (i) to (v) failed. Also replace "near or above 0.6" and "clearly above" in section 10(4) by numbers (or state it is purely discretionary) so the slot decision is not gameable.

**M3. Null A (and therefore G1a, G1b, category P) is anti-conservative when currency returns are persistent or share a carry-crash factor; the calibration only used iid Gaussian noise, and the section 8 sentence "False positives are controlled" is unsupported.**
- Where: section 6 (Null A, one relabelling per 12-month block), section 8 "Reading of the calibration" first bullet and last bullet (which frames the missing tails and crashes only as a false-NEGATIVE issue).
- Evidence (my simulation, script `rev_null_fpr.py` / `rev_null_fpr2.py`; synthetic spot returns on the real rates and calendar, planted so that true expected S0 excess return is 0, i.e. UIP holds in expectation; 300-400 panels each, 399 permutations; standard errors about 1.3-2.0 points). Rejection rates at 0.05 for V1 unless stated:

  Mechanism: the real V1/V2 weights are persistent (I measured that the V1 ranking is unchanged in 182 of 221 months, rates only), so the real portfolio loads on the same currencies for years; with multi-year currency drift or a common crash factor correlated with the ranking, the real Sharpe has a larger sampling sd than the block-permuted null (0.35 vs 0.25 in the 4 % world; 0.26 vs 0.23 in the crash world). Momentum evidence (the R3-1 result the author already knows, Sharpe about +0.5 gross) is itself a sign that variance ratios above 1 are plausible on this panel. The full-sample relabelling removes the inflation caused by persistence (4.7-5.7 % in all trend worlds) at a small cost in power (planted S0 0.5: 62 % vs 67.5 % rejection; planted S0 0.7: 86 % vs 90.5 %); it does not fix the crash-factor case (11.7 %), which no permutation null can, because the exposure is systematic.
- Why it matters: category P is reported as "a carry premium is detectable at the interbank-accrual level"; in a world with a mild variance ratio of 1.3 that statement is wrong 9 % of the time, and in a 2.3 world 25 %. E is protected by the S1 gates (at most 4 % in these worlds), so the damage is to P and to the unadjusted headline p-values.
- Minimal fix (pre-run revision, logged): (a) add Null A' = one uniform relabelling of the live currencies for the entire sample (`block=Kp` already works in `null_distribution`), and define G1a on `max(p_block12, p_full)` before Holm; (b) add the "slow drift" and "crash" worlds above to `calibrate` (they are about 40 lines) and report the false-positive rows; (c) replace "False positives are controlled" by the table, and state that under common-crash exposure P is overstated by roughly a factor of 2 and cannot be corrected by the null.

## Should-fix (not blocking, but each is a real weakness)

**S1. Rate publication lag and the 3-month proxy.** Information-wise lag 1 is not look-ahead: the average of month m-1 is complete at the end of m-1 and every daily fixing is public, so a live system can compute it itself, and the average is on average 1.5 months old at the decision. But the registered source (FRED/OECD) does not publish it that early: your own fetch on 2026-11-03 had USA at 2026-09 and JPN at 2026-08 (data notes table, section 1), i.e. a publication lag of about 5 weeks or more for some series, so a decision "at the end of month m" cannot be reproduced from this source with lag 1. Rankings are persistent, so I expect little effect, but the prereg should say so and make the lag-2 sensitivity (already produced) a stated robustness condition (for example "SR(S1, lag 2) > 0" as a reported check beside the categories, not an extra gate). Separately, owner decision 1 (policy or overnight rates) should be taken BEFORE the run: the 3-month series embeds expected rate changes and bank-credit premia (2007-2012), which inflate S0 accrual for currencies in hiking or stress periods, and the "optional follow-up after the DEV result" is otherwise a free second look that cannot change eligibility but will be read.

**S2. Analytic power formula uses the wrong variance for an annualised Sharpe.** `power_table()` (fx_carry.py line 635) uses SE = sqrt((1 + SR^2/2) f / T); with monthly data and an annualised SR the term is SR^2/24 (verified: empirical sd of the annualised Sharpe of 221 iid months is 0.2355 at SR 0.5, 0.2385 at SR 1.0; the code formula gives 0.247 and 0.285). Direction is conservative (power understated: 0.69 vs 0.65 at SR 0.5; 0.94 vs 0.88 at 0.75; SR for 80 % power 0.58 vs 0.64 single test, 0.70 vs 0.79 first Holm step, f = 1). Fix the formula, regenerate `power_table.json`, update `test_power_table_values` and the section 8 table and the "0.65 to 0.95" sentence. The calibration table (synthetic, empirical) is unaffected and matches the JSON exactly.

**S3. Categories U and N carry almost no information and U is named misleadingly.** At lambda = +1 (true excess 0) the calibration gives U 64 % and N 32 %: the split is just the sign of the largest of three noisy Sharpes. Merge U and N ("no detectable premium", with the sign of the S0 Sharpes reported), or at least say in the table that U and N are not distinguishable evidence. There is also no category for a significantly negative result (reverse carry); all tests are one-sided. State that explicitly.

**S4. V3 is not blind either.** Section 0 declares the momentum control unblind because R3-1 FX momentum results were seen, but V3 (carry plus 12-1 momentum) enters the Holm family and can be the frozen candidate. Say so in section 0, or drop V3 from the candidate family (then K = 2). Also pre-specify what M passing G1a means: as written ("looks at the calibration before deciding which") it is discretionary; better: M never changes the category and is reported.

**S5. Deterministic tie-break is arbitrary and biased.** `_rank_weights` breaks ties by currency order, so among tied scores the lower-index currency is long and the higher-index (NOK, SEK) short. My planted constant-rate probe shows SEK shorted among tied currencies. In the real DEV rates exact ties across the long/short boundary occur at 2 decisions (2010-06-30 and 2020-08-31; 7 decisions have any tie), so the effect is small; pre-specify "ties keep the previous month's holding" or an alphabetical rule and say it is arbitrary.

**S6. Small ambiguities.** (a) G3a "three best calendar years" is computed over all years in the series including the partial 2021 (`gates`, line 595); say whether 2021 is eligible. (b) FINAL condition (iv) (ex-USD ranking S1 > 0) is not a DEV gate, so a DEV-eligible candidate can be built to fail a FINAL condition that DEV only reports; either add it to DEV as reported-before-freeze or state the owner sees it first. (c) Execution day: on 1 January the nominal ED is 1 Jan but the first broker bar is 2 Jan (about 10 of 222 decisions per pair, 12 for NOK): the accrual starts one day early and ends one day early; immaterial, state it. (d) The USD slot is in the ranking: USD sits in the long set in 25 % and the short set in 39 % of decisions (rates only), so the portfolios carry a sizeable net USD position; report the mean net USD exposure beside BL.

**S7. Spread cost depends on later bars and the D1 spread field is of unknown timing.** Already disclosed as cost-only; also state that the MT5 D1 `spread` is a single recorded value per bar (not shown to be the open or the rollover value), which is another reason the floor is an assumption. Immaterial against the mark-up.

## Notes: things checked and found fine

No double counting: spot is price only, accrual is interest only, mark-up is separate. Weekends and the Wednesday triple are the same calendar days allocated differently; the telescoping test holds. Day counts (365 for GBP, AUD, CAD, NZD; 360 otherwise) are the money-market conventions.
3. **Calendar and NOK.** Decision dates, 222 decisions, 221 periods verified. From dates alone: USDNOK has 255 bars at the 2007-01-31 decision (252 needed), so it is first live exactly there and 49 of 221 periods have nine live currencies, as registered. The comparison with R3-1: the same rigor (calibration, nulls, stop rule, FINAL guard), better (planted-carry calibration, null of the sizing), worse only in M1 (R3-1 was committed first).
